# Model as a Service - Knowledge Base User Story

| Item                      | Description |
|---------------------------|-------------|
| ***Summary***                   |As an application developer, I want to use a standardized API to create, manage, and populate knowledge bases with documents, so that I can build knowledge-intensive applications (like intelligent customer service or enterprise wikis) with fine-grained access control and full traceability. I also want to register external callable tools under a knowledge base, so that they can be associated with Q&A assistants and invoked automatically by the LLM during answer generation (agent-style behaviour), or tested directly through the platform's execution path. |
| ***Roles, Actor(s) and scope*** |**Roles:** Application Developer, API Consumer (Application Server)<br/>**Actors:** Application Service Provider, End-Users interacting with the knowledge-based application.<br/>**Scope:** Full CRUD (Create, Read, Update, Delete) lifecycle management of knowledge base resources, document upload, and tool registration (create/read/update/delete tools, invoke a tool via `callTool`).|
| ***Pre-conditions***            |<ul><li>The API Consumer (application server) is onboarded to the CSP's API platform.</li><li>The API Consumer has successfully subscribed to the Knowledge Base API product.</li><li>The API Consumer has obtained a valid OAuth 2.0 access token with the required scopes for the intended operation (e.g., knowledge-base:knowledge-bases:create, knowledge-base:tools:create, knowledge-base:tools:call).</li><li>The tool endpoints registered via `createTool` are reachable from the API provider's environment and use the `https` scheme.</li></ul>             |
| ***Activities/Steps***          |Starts when: The API Consumer application server makes an authenticated API request (e.g., POST /knowledge-bases to create a new knowledge base, POST /knowledge-bases/{knowledgeBaseId}/documents to upload a document, POST /knowledge-bases/{knowledgeBaseId}/tools to register a tool, or POST /knowledge-bases/{knowledgeBaseId}/tools/{toolId}/call to test a registered tool through the platform's execution path).<br/>Ends when: The requested operation is completed by the API server and a success or error response is received (e.g., 201 Created for a successful creation, 200 OK with a `ToolCallResponse` for a `callTool` invocation).             |
| ***Post-conditions***           |The state of the knowledge base system is changed according to the operation (e.g., a new knowledge base is created, a document is added, a tool is registered and available for association with a Q&A assistant via `qa-assistant-manage`, a tool is invoked and its execution result is returned). Registered tools can be associated with assistants and may be invoked automatically by the LLM during `queryAssistant` answer generation. Only documents whose indexing `status` is `READY` participate in answer generation. The API consumer can proceed with its application logic.             |
| ***Exceptions***                |<ul><li>401/403 Unauthorized/Forbidden: Invalid, missing, or expired access token; lack of required OAuth scope.</li><li>400 Bad Request: Invalid input (e.g., missing required 'name' field, invalid document format, request body with undeclared properties, tool `url` not using `https` or violating the SSRF constraints).</li><li>404 Not Found: Referenced resource (e.g., knowledgeBaseId, documentId, toolId) does not exist.</li><li>409 Conflict: A knowledge base or tool with the same `name` already exists (name MUST be unique within a knowledge base).</li><li>415 Unsupported Media Type: Attempting to upload a document type not supported (only DOC, PDF, TXT, CSV are accepted).</li><li>422 Unprocessable Content: Tool is disabled or arguments are semantically invalid (`KNOWLEDGE_BASE.TOOL_INVALID_INPUT`, `KNOWLEDGE_BASE.TOOL_DISABLED`).</li><li>500 Internal Server Error: A platform-internal error occurred during processing. Note: failures of the *upstream tool* - including an upstream rate-limit, an upstream server error or a timeout - are NOT reported as HTTP errors on `callTool`; they are returned in the 200 envelope as `success=false`, with `statusCode` mirroring the upstream HTTP status and `contextCode` set to `KNOWLEDGE_BASE.TOOL_RATE_LIMITED`, `KNOWLEDGE_BASE.TOOL_EXECUTION_FAILED` or `KNOWLEDGE_BASE.TOOL_TIMEOUT`.</li></ul>             |
